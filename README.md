# 캐릭터 챗봇 프로젝트 베이스 코드

5기 중간 프로젝트를 시작하기 위한 **실행 가능한 예시**입니다. Flask 웹 화면과 채팅 API, 검색·답변 생성의 연결 지점을 제공합니다. 처음 실행하면 API 키 없이 데모 답변이 나옵니다. 캐릭터, 화면, 모델, 서버 구조, 배포 방법은 기획에 맞게 바꿀 수 있습니다.

> [!TIP]
> **함께 지키고 싶은 학습 방향**
>
> Hateslop 학회원은 스스로 배우고자 하는 의지가 있는 사람들입니다. 단순히 제출을 위한 과제를 만드는 데 그치지 않고, 스스로 탐구하고 성장할 수 있다고 믿습니다.
>
> 오늘날 AI로 정답을 찾는 일은 어렵지 않습니다. 중요한 것은 답에 이르는 사고 과정과 추론 능력, 더 나은 답을 찾으려는 문제 해결력입니다.

> **데모의 한계:** 현재 답변은 입력을 되돌려주는 예시이며 AI 답변이나 RAG 결과가 아닙니다. 실제 프로젝트에서는 캐릭터 답변 생성과 답변별 이미지 선택을 구현하고 결과를 검증해야 합니다.

## 프로젝트에서 완성할 것

이 프로젝트의 목표와 제출 기준은 [프로젝트 가이드](docs/PROJECT_GUIDE.md)에 정리되어 있습니다. 핵심은 캐릭터 설정을 반영하는 실제 대화, 답변 내용에 맞는 이미지 출력, 공개 URL에서의 시연입니다. 자료가 있는 기획에는 검색을 권장하고, 대화 메모리나 다른 기능은 제품에 필요할 때 설계합니다.

현재 베이스는 Python 3.12·Flask 앱, HTML/CSS/JavaScript 화면, 검색·생성·이미지 선택 모듈 경계를 제공합니다. 이것은 출발점이며, 화면 프레임워크·서버 구성·배포 플랫폼을 고정하지 않습니다.

## 데모 실행: 한 가지 방법을 선택하세요

아래 방법 중 하나로 서버를 실행하고 **캐릭터 소개 → 대화 시작 → 메시지 전송 → 데모 답변**을 확인하세요. 여기까지는 API 키나 모델 설치가 필요하지 않습니다. 캐릭터 설정과 실제 기능 구현은 팀의 기획이 정해진 뒤 진행합니다.

### Conda

수업에서 사용한 Conda로 시작할 수 있습니다. 프로젝트 루트에서 실행하세요. 현재 Dockerfile과 같은 Python 3.12를 예시로 사용합니다.

```bash
conda create -n chatbot-base python=3.12 pip
conda activate chatbot-base
python -m pip install -r requirements.txt
python app.py
```

<http://localhost:5000>에서 화면과 데모 답변을 확인하세요. 가상환경을 만든 뒤 설치하는 패키지는 `requirements.txt`를 기준으로 합니다.

### Docker Compose

팀원 간 실행 환경과 명령을 맞추고 싶다면 Docker Desktop 또는 Docker Engine과 Compose를 설치한 뒤 실행하세요.

```bash
docker compose up --build
```

<http://localhost:5001>에서 확인합니다. Docker 사용 시 호스트에 Conda/venv를 따로 만들 필요는 없습니다. 의존성을 바꾸면 이미지를 다시 빌드하세요. 이 경로로 컨테이너 안에서 테스트하는 방법은 [로컬 실행 가이드](docs/LOCAL_SETUP.md)에 있습니다. Docker는 최종 기술 선택의 필수 조건이 아닙니다.

### Python venv

Conda나 Docker를 사용하지 않는 팀을 위한 선택지입니다.

```powershell
# Windows PowerShell 예시
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
python app.py
```

```bash
# macOS / Linux
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
python app.py
```

브라우저에서 **캐릭터 소개 → 대화 시작 → 메시지 전송**을 확인하세요. `.env`는 데모 실행에 필수는 아닙니다. PowerShell에서 `py -3.12`가 없다면 설치된 Python 실행 명령을 사용하세요. 자세한 운영체제별 명령은 [로컬 실행 가이드](docs/LOCAL_SETUP.md)에 있습니다.

## 이 베이스의 범위

| 제공하는 것 | 팀이 구현하거나 바꿀 것 |
| --- | --- |
| 메인·소개·대화의 **예시 화면**과 기본 반응형 CSS | 팀의 콘셉트에 맞는 UX·디자인. 화면 전면 교체 가능 |
| 메시지 전송 JS, 입력 검증, JSON 응답을 가진 **예시 API** | 실제 AI 답변, 자료 검색, 오류·품질 개선. API 계약 변경 가능 |
| 자료 검색 → 답변 생성 → 이미지 선택 → 응답 조립의 **기본 코드 구조** | 모델·검색기·이미지 선택기 연결, 저장소, 필요한 기능과 모듈 추가 |
| 캐릭터 설정 파일과 가상 연습 자료 | 실제 캐릭터·자료의 준비와 검색 인덱스·모델 연결 |
| Conda/venv 실행 명령, 개발용 Compose, 배포용 Dockerfile | 팀의 의존성, 데이터 저장소, 배포 구성과 공개 URL 검증 |

현재 코드는 화면과 API가 연결된 데모입니다. AI 챗봇 기능은 아직 구현되어 있지 않습니다. 세 화면의 흐름, Flask, 단일 캐릭터, `/api/chat` 형식, 색상·레이아웃은 과제 제약이 아닙니다. React/Next.js 등 별도 프런트와 API 서버를 구성해도 됩니다.

팀의 프로젝트를 시작하면 **팀 저장소의 루트 README**를 실제 서비스 소개와 실행·테스트·배포 방법에 맞게 고치세요. 이 저장소의 `docs/`는 현재 Flask 데모를 설명합니다. 구조를 바꾼 팀은 필요한 내용만 참고하고, 실제 구현과 맞지 않는 문서는 고치거나 정리하면 됩니다.

## 어디를 바꾸나요?

| 원하는 작업 | 파일 |
| --- | --- |
| 캐릭터 이름·소개·첫 인사·성격·말투·세계관 | `config/chatbot_config.json` |
| 자료 검색 | `services/retriever.py` |
| 모델 호출·답변 생성 | `services/generator.py` |
| 대화용 이미지와 메타데이터 준비·답변별 이미지 선택 | `public/assets/images/`, `data/images/`, `services/image_selector.py` |
| 검색·답변·이미지 결과를 API 형식으로 조립 | `services/chatbot_service.py` |
| API 요청 검증·화면 라우팅 | `app.py` |
| 화면 구성 | `templates/`, `public/assets/css/`, `public/assets/js/` |
| 챗봇이 참고할 원본 자료 | `data/knowledge/` |
| 배포 방법 | `docs/DEPLOYMENT.md` |

자료 파일을 `data/knowledge/`에 넣는 것만으로는 검색이 되지 않습니다. 자료를 나누고, 검색 인덱스를 만들고, 찾은 내용을 답변에 반영하는 코드는 팀이 구현해야 합니다. 이미지를 폴더에 넣는 것만으로 답변에 맞춰 선택되지도 않습니다. 수업에서 배운 ChromaDB는 좋은 출발점이지만 필수 저장소는 아닙니다.

**실제 AI 답변 연결 방법**은 [OpenAI 모델 연결 가이드](docs/MODEL_SETUP.md)에 있습니다. 운영진이 제공하는 API 키를 `.env`에 설정하고, `services/generator.py`의 데모 답변을 모델 응답으로 바꾸면 됩니다. 다른 모델 공급자를 선택한 팀은 같은 생성기 연결 지점에 맞춰 구현하고, 필요한 인증 정보와 사용 조건을 확인하세요. 검색과 이미지 선택의 입력·반환값은 [구조 설명](docs/ARCHITECTURE.md)을 보세요.

OpenAI 모델 연결은 **`gpt-6-luna`와 `none`**으로 시작합니다. `none`을 기본으로 두고, 같은 질문으로 확인했을 때 특정 기능에서 맥락 반영이 부족한 경우에만 그 기능의 호출을 `low`로 바꿔 비교하세요. `medium`은 `low`로도 명확한 요구사항을 충족하지 못한다는 테스트 결과가 있을 때만 예외적으로 검토합니다. 높은 강도를 선택했다고 답변 품질이 자동으로 좋아지는 것은 아니므로, 기본 설정으로 사용하지 않습니다. 호출별 설정 방법은 [모델 연결 가이드](docs/MODEL_SETUP.md)에 있습니다.

## 프로젝트 구현 흐름 예시

아래는 **데모 실행 이후 프로젝트를 만드는 동안** 참고할 순서입니다. 초기 설정 체크리스트가 아니며, 기획과 역할 분담에 맞춰 순서를 바꾸거나 병행해도 됩니다.

1. 위 실행 방법으로 화면과 데모 답변을 확인합니다. 이때는 API 키가 필요 없습니다.
2. `config/chatbot_config.json`에 캐릭터의 이름·첫 인사·성격·말투·세계관을 적고, 대화에서 지켜야 할 규칙을 정합니다.
3. `services/generator.py`에서 데모 문장을 모델 답변으로 교체합니다. OpenAI 연결은 [모델 연결 가이드](docs/MODEL_SETUP.md)를 따라 운영진이 제공한 키를 설정하고 짧은 질문으로 확인합니다.
4. 질문에 따라 세계관 자료가 필요하다면 `data/knowledge/`의 원본을 정리하고 `services/retriever.py`에 검색을 붙입니다. 자료를 넣는 것과 검색 인덱스를 만드는 것은 별도 작업입니다. [RAG 흐름](docs/ADVANCED_TOPICS.md#최소-rag-흐름)
5. 대화용 이미지와 장면 설명을 준비합니다. 감정·상황 라벨, 장면 설명과 답변의 임베딩 유사도, 이미지 자체 임베딩 등 기획에 맞는 선택 방식을 구현합니다. 팀이 준비한 이미지와 테스트 답변으로 선택·생략이 적절한지 확인합니다. [이미지 자료 위치와 구현 방향](data/images/README.md)
6. `services/chatbot_service.py`에서 답변과 이미지가 연결되는지 확인합니다. 자료 검색을 쓴다면 개발 중 검색 결과도 점검합니다. 화면을 다듬고 공개 URL에서 전체 대화 흐름을 시험합니다. [배포 가이드](docs/DEPLOYMENT.md)

## API 키와 환경 파일

데모에는 API 키가 필요하지 않습니다. OpenAI 모델을 연결할 때 사용할 API 키는 운영진이 제공합니다. 전달받은 키는 로컬 `.env` 또는 배포 플랫폼의 비밀 환경 변수에만 보관하세요. `.env.example`에는 변수 이름과 공개해도 되는 기본 설정만 적습니다. **README·다른 Markdown·코드·이슈·스크린샷에 실제 키를 적거나 팀 채팅에 다시 공유하지 마세요.** `.gitignore`는 `.env`와 `.env.*`를 제외합니다. 커밋 전 `git status --short`로 파일 목록을 확인하고, `git check-ignore .env`로 제외 여부를 확인하세요. 키가 노출되면 운영진에게 바로 알려 교체를 요청하세요. 자세한 내용은 [로컬 실행 가이드](docs/LOCAL_SETUP.md)를 보세요.

초기에는 **데모 응답으로 연결을 확인한 뒤 정해진 질문 몇 개만 API로 시험**하세요. OpenAI 연결과 모델별 답변·사용량 비교는 [모델 연결 가이드](docs/MODEL_SETUP.md)와 [모델 선택 가이드](docs/MODEL_CHOICE.md)를 참고하세요. 제공된 키의 사용량은 운영진이 안내한 범위에서 확인하고, 불필요한 반복 호출은 피합니다.

## 현재 데모 API

`POST /api/chat`에 JSON을 보냅니다.

```json
{"message":"안녕!","username":"헤슬"}
```

성공 응답:

```json
{"reply":"헤슬님, ...","image":null,"sources":[]}
```

`reply`는 필수 문자열, `image`는 이미지 URL 또는 `null`입니다. `sources`는 개발 중 검색 결과를 확인할 수 있도록 남겨 둔 자료 제목 목록이며, 채팅 화면에는 표시하지 않습니다. 지금은 검색 기능이 없어 빈 목록입니다. 현재 서비스 코드는 검색된 자료 제목을 모두 `sources`에 넣으므로, 이것을 실제 답변의 인용 목록으로 취급하면 안 됩니다.

입력 오류는 `400` 또는 `413`과 `{"error":{"code":"...","message":"..."}}` 형식으로 응답합니다. 서버 오류는 `500`입니다. `GET /health`는 프로세스가 응답하는지 확인하며 검색 품질이나 외부 서비스 상태를 보증하지 않습니다.

## 프로젝트 기준과 자유도

- **결과 기준:** 팀의 캐릭터와 대화할 수 있는 서비스, 설명 가능한 기술 선택, 실제 사용 시나리오의 검증, 공개 접속 URL을 준비합니다.
- **자료 활용:** 캐릭터의 세계관·기록·FAQ처럼 외부 자료가 있는 기획은 자료의 원래 출처와 사용 권한을 기록하고, 검색한 내용이 답변에 반영되는지 개발 중 확인하세요. RAG가 기획에 불필요하다면 이유, 대신 구현할 기술 요소, 검증 방법을 프로젝트 문서에 적으세요.
- **구현 선택:** ChromaDB·LangChain·OpenAI·Flask·Docker·Render 중 어느 하나도 최종 결과물의 필수 기술로 지정하지 않습니다. 프런트 화면 수, 프레임워크, 서버 분리 여부, API 형식도 팀의 제품에 맞게 정할 수 있습니다.
- **답변별 이미지:** 대화 내용과 어울리는 이미지를 답변에 함께 보여줍니다. 감정·상황 라벨, 장면 설명과 답변의 임베딩 유사도, 이미지 자체 임베딩 등 기획에 맞는 방식을 선택합니다. 과제에서 임베딩 유사도를 요구한다면 라벨에 따른 경로 선택만으로 끝내지 않습니다. 프로필 이미지를 고정해서 보여주는 것만으로는 답변별 이미지가 구현된 것이 아닙니다. 자세한 출발점은 [이미지 자료 안내](data/images/README.md)에 있습니다.
- **선택 확장:** 이전 대화를 저장·반영하는 **대화 메모리**는 기획에 필요할 때 추가합니다. 화면 내 메시지 나열만으로는 서버가 이전 대화를 기억하지 않습니다.

과제 범위의 자세한 판단 기준은 [프로젝트 가이드](docs/PROJECT_GUIDE.md)에, 현재 코드와 확장 지점은 [구조 설명](docs/ARCHITECTURE.md)에 있습니다.

## 배포 경로

이 베이스 코드는 한 Flask 앱이 화면과 API를 함께 제공하도록 구성했습니다. Render의 웹 서비스나 Vercel의 Flask Function으로 검토할 수 있습니다. 프런트와 API를 분리하거나 Cloudflare Workers를 쓰려면 정적 파일 위치, API 주소, Python 패키지 호환성, 지속 저장소를 다시 설계해야 합니다. **특정 플랫폼을 강요하지 않습니다.** [배포 가이드](docs/DEPLOYMENT.md)의 선택표와 점검 목록을 먼저 보세요.

## 검증

```bash
python -m unittest discover -s tests -v
```

`tests/`는 현재 Flask 데모의 화면·정적 파일·API·서비스 연결을 확인하는 예시 테스트입니다. 개발 중 로컬이나 Docker Compose에서 실행할 수 있습니다. 실제 검색 품질과 모델 답변의 정확도는 별도로 평가하세요. 팀이 구조를 바꾸면 테스트를 그 구조에 맞게 고치거나 교체하면 됩니다. 배포용 Docker 이미지에는 테스트와 문서를 복사하지 않습니다.

### 1. 공개 URL

공개 URL을 준비하고, 다른 사람이 별도 개발 환경 없이 핵심 흐름을 시연할 수 있는지 확인하세요.

- 첫 화면부터 채팅 화면까지 이동할 수 있는가?
- 실제 모델 답변과 답변별 이미지가 동작하는가?
- 자료가 있는 질문과 없는 질문, API 실패 상황에서 적절히 응답하는가?
- CSS·JavaScript·이미지가 모두 공개 URL에서 열리는가?

[배포 가이드의 공개 URL 점검 목록](docs/DEPLOYMENT.md#4-공개-url에서-최종-확인)으로 마지막 확인을 할 수 있습니다.

### 2. 프로젝트 저장소와 README

팀 저장소의 README는 결과물의 사용 방법과 팀의 판단 근거를 다른 사람이 이해하고 재현할 수 있게 작성합니다. 이 베이스 README를 그대로 유지할 필요는 없습니다. 아래 항목을 프로젝트에 맞게 채우세요.

1. **프로젝트 소개와 주요 기능:** 누구를 위한 서비스인지, 어떤 대화 경험을 만들었는지 설명합니다.
2. **아키텍처와 데이터 흐름:** 다이어그램이나 단계 목록으로 브라우저·API·검색·모델·이미지 선택이 어떻게 연결되는지 보여줍니다.
3. **기술 스택과 선택 이유:** 기술 이름만 나열하지 말고, 어떤 요구를 해결하려고 선택했는지 적습니다. 사용하지 않은 기술도 이유가 있으면 설명합니다.
4. **실행과 테스트 방법:** 필요한 환경 변수의 이름, 실행 명령, 확인한 질문과 결과를 적습니다. 실제 API 키 값은 쓰지 않습니다.
5. **개발 중 문제와 해결:** 문제가 어떻게 나타났는지, 원인을 어떻게 찾았는지, 어떤 방법을 시도했고 무엇으로 해결했는지 기록합니다.
6. **개선 노력과 검증 결과:** 품질·응답 시간·검색 결과 등을 개선했다면 비교 방법과 표본을 함께 적습니다. 측정하지 않은 수치나 효과를 만들어 쓰지 않습니다.
7. **알려진 제한과 아쉬운 점:** 구현하지 못한 기능, 현재 잘 동작하지 않는 조건, 다음에 개선할 일을 구체적으로 적습니다.
8. **회고:** 구현과 협업에서 새로 배운 점, 다음에 다르게 해볼 점을 적습니다.

최종 제출할 때는 각 팀의 README에 완성한 서비스의 주요 화면 스크린샷을 넣으세요. 캡처에 API 키나 개인정보가 보이지 않는지 확인하세요.

README의 시작점으로 다음 목차를 사용할 수 있습니다.

```markdown
## 프로젝트 소개
## 화면 미리보기
## 주요 기능
## 아키텍처와 데이터 흐름
## 기술 스택과 선택 이유
## 실행 및 테스트
## 개발 중 문제와 해결
## 개선 결과와 검증 방법
## 알려진 제한과 다음 개선점
## 회고
```

자료를 사용했다면 출처와 공개·사용 권한을 확인하세요. API 키·비밀번호는 `.env`나 배포 플랫폼의 비밀 환경 변수에만 두고, 코드·문서·커밋·스크린샷에는 넣지 않습니다. 발표 자료를 별도로 요청받았다면 위 내용을 바탕으로 서비스 흐름, 아키텍처, 핵심 선택, 검증 결과를 보여주세요.

## Git 협업을 시작한다면

`main`을 배포 가능한 상태로 두고, 작업별 브랜치를 만들어 진행하는 방식을 권장합니다. 브랜치 이름은 팀에서 정하세요. 작업을 작게 나누어 커밋하고 GitHub Pull Request로 합치면 변경 내용을 서로 확인하기 쉽습니다. 커밋은 `feat: 답변 생성 연결`, `fix: 빈 메시지 처리`, `docs: 실행 방법 보완`처럼 목적을 앞에 적어주세요. 처음 사용하는 팀은 [팀 협업 가이드](docs/TEAM_WORKFLOW.md)의 명령 예시를 따라가면 됩니다.
